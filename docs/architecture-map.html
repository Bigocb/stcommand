Standing Orders · engine architecture

Fleet Control Plane

An autonomous SpaceTraders fleet, rebuilt as a reconciled cluster. Every component below has a counterpart in Kubernetes or a service mesh, and the mapping is close enough to be load-bearing rather than decorative.

Control plane — decides, never touches a ship Data plane — executes, never decides a route

The failure that started it

Why the two planes had to separate

Nothing here was slow because of the language or the hardware. The fleet is capped at roughly one and a half API requests per second, shared across every ship. The problem was that control decisions were sitting on the data path, so anything that waited made everyone wait.

The coordinator loop flew ships itself, blocking for the whole transit. Ship agents planned their own routes from a private copy of the world that was frozen when they were built. And the task runner is strictly sequential, so a single mining loop — sixty extractions, each ending in a cooldown sleep — could hold every other ship in the tenant, rescue included, for the better part of an hour.

The model

Controllers decide · the executor acts · the registry is read by both

Doctrine is the manifest. Controllers compare it against observed state and emit one intent per ship. An arbiter resolves competing intents by priority so exactly one wins. The executor takes that intent and makes a single API call, then reports what it saw. Nothing above the executor ever waits on a ship.

Copies versus a reference

The single largest source of live bugs

Each ship agent used to be handed a snapshot of the world when it was constructed, and nothing gave it back afterwards. Every staleness failure got patched by adding another push. The registry removes the copies entirely, so there is nothing left to push.

The four rules

Each one names a mistake the old design made

Controllers never call the kubelet

Nothing above the executor awaits a ship. The coordinator flying a ship itself is the API server opening a shell on a node.

The kubelet never chooses a route

A ship picks endpoints within policy — nearest healthy pump, nearest yard. It never picks which good to trade. Route is RDS; endpoint is EDS.

Level-triggered, not edge-triggered

Every pass is observed versus desired, act on the difference. There is no code path that runs "after" an action completes.

Status is written by the observer

The control plane's view of a ship comes from that ship's own step reports, never from a poll racing the executor.

Where the analogy breaks

One shape the mapping tempts you into is wrong: a pod per hull. The API limit is per IP and shared by the entire fleet, so distributing ships across pods would mean every ship calling a central token service before every request, to arbitrate a resource that permits roughly one and a half operations per second. It also forces the registry back into per-pod copies, which is the exact bug class the registry exists to delete.

The correct unit is the tenant. That is a real fault domain, a real resource boundary, and the code is already shaped for it. Single-threaded execution is also quietly buying correctness: the route claim is race-free because the event loop cannot preempt it mid-decision. Goroutines would turn that into a mutex somebody has to remember.

Migration

Each step independently shippable

  1. Data plane cannot block done

    Cooldowns yield with a resume time exactly as transits already did. Extraction became resumable, so a ship interrupted mid-session keeps mining instead of hauling a five-unit hold to market.

  2. Registry by reference done

    All four agent classes read one live world. The private caches, the reseed pushes and the explore-time repair hook are deleted.

  3. One executor next

    Collapse the four copies of navigate, dock and refuel into a single step function. This is where in-system and cross-system flight stops being four separate implementations.

  4. Intents and arbiter

    Repair, rescue, explore and manual dispatch become intents. The blocking coordinator path disappears with them.

  5. Controllers

    The existing maybe-shaped functions return proposals instead of acting, and the tick runs them as a list.

  6. Telemetry-driven registry

    Step reports feed observed state; the dashboard shows intent against observed, per ship.
